# TSF Empty Factory: design

Read `src/shared/types.ts` first. It, `src/shared/events.ts`, `src/shared/capabilities.ts` and `src/core/service-api.ts` are the contract between every module. Change them only together with every consumer, and update this file in the same change.

Spec: `spec/tsf-empty-factory.md`. Phases P1 to P8 are the spec's milestones M1 to M8 (M0, the pw-ui `./theme` export, is released in pw-ui 0.6.0). All eight are built; this file describes the built system. P8 (acceptance demo, SKILL.md, this file) adds no capability, route or tool, so `BUILT_THROUGH_PHASE` stays 7. The exe.dev deployment check (section 12) was run on 2026-11-03.

## 1. Overview and principles

`/tsf` installs an Empty Factory next to a repository: a web app with one durable pi-durable agent, three panes (pages, focus, agent), and every core capability as data. The app is resident in the skill directory; the host project receives only `tsf/`.

| Principle | How the design holds it |
|---|---|
| Durable | One pi-durable 1.5.0 Harness on `tsf/data/agent.sqlite`. A chat POST only submits; turns run in the server; output reaches browsers through SSE fed by `Conversation.watch`. Restart = open, `resume()`, auto-continue an interrupted run. |
| Parity | One `Service` (`core/service.ts`, contract `core/service-api.ts`). Routes and tools are thin callers. `shared/capabilities.ts` lists Service method, routes, tool, `data-cap`; `tests/unit/parity.test.ts` enforces it. |
| Liquid | Layout, navbars, theme, hotkeys, animations live in one UI config document; prompts, tools, model, compaction, cron live in `tsf.sqlite` settings tables. Every change publishes an `AppEvent`; the open page applies it with no reload. |
| Layers | A layer is a folder with `manifest.ts` (LayerManifest) and `extension.ts` (pi-durable extension factory). Built-ins in `src/layers/`, project layers in `tsf/layers/`. |
| Ceiling | `tsf/permissions.json` + `--tools` are read once at startup into a frozen `Ceiling`. Tools outside it are never registered, and the guard hook in `factory_harness` answers any call to one with a `blocked` result naming the ceiling (section 8). No route or tool writes the file. |

Out of scope (spec 3): PW capability layers, image generation, model tiers, non-OpenRouter providers, approval UI, auth, multi-user, subagents.

Host project after install (`tsf/`): `mod.just`, `permissions.json`, `.env.example`, `pages/Start Here.md`, `layers/.gitkeep`, `app/` (P9, below), `data/` (gitignored: `agent.sqlite`, `agent.sqlite.lock`, `server.json`, `tsf.sqlite`, `logs/`). `install.sh` appends `tsf/.env` and `tsf/data/` to `.gitignore`, and registers a bare `mod tsf` line (with the mod's header comment above it) in the root justfile, or stamps a new justfile. It refuses inside the skill directory and reports `kept` instead of failing when the root already defines a recipe named `tsf` (just's "Module defined as a recipe").

**The project's own app (`tsf/app`, P9 "Liquid core").** Unless `--no-app` (or `TSF_INSTALL_NO_APP=1`) is given, `install.sh` copies the skill's `app/` into `tsf/app` (everything except `node_modules`, `dist`, `.vite`, `test-results`, `playwright-report`; `tests/` stays; `vendor/` comes with it, so the relative `@pw/ui` spec still resolves) and writes `tsf/app/.tsf-base`, JSON `{ appVersion, skillDir, commit, date }` (`appVersion` is the skill app's `package.json` version, `commit` is `git -C <skill> rev-parse HEAD` or null when the skill is not in a git checkout). The project then owns its factory source: `mod.just` runs `tsf/app/bin/tsf.mjs`, the server runs `tsf/app/src`, the web is built from `tsf/app/src/web`, and the agent may edit all of it (RootedEnv protects only `tsf/app/node_modules` and `tsf/app/.tsf-base`). Report words: `stamped tsf/app/ (copy of the skill app; tsf/app/.tsf-base records its base)`; a second run reports `kept tsf/app/` and leaves the copy untouched (a merge of a newer skill into an edited copy is not built, section 14). `.gitignore` also gets `tsf/app/node_modules/`, `tsf/app/dist/` and `tsf/app/.vite/`. The copy needs its own `npm install` (the launcher does it on the first start, step 2 below, and again when `package.json` changes: the agent may add a dependency and restart).

**`appDir` resolution (`core/paths.ts`).** `ownAppDir` is the app this process runs from, derived from `import.meta.url`. `skillDir` is `TSF_SKILL_DIR` when set and valid, else (when running from a project copy) the `skillDir` in `.tsf-base`, else the parent of the app. `projectPaths(root).appDir` is always `ownAppDir`: code, built-in layers, web source and dist come from the tree the server runs from, where its node_modules live. `projectAppDir(root)` reports `<root>/tsf/app` when it holds a `package.json`. A server started from the skill's launcher in a project that has a copy (a unit installed before the copy existed, or `node <skill>/app/bin/tsf.mjs` by hand) runs the skill's app untouched and logs `startup.app_mismatch { running, project }`; loading anything from the copy would fail on its missing node_modules (found on the first VM deploy). `just tsf start` and a reinstalled unit pick the copy's launcher.

**Install target.** `install.sh` installs into its working directory (`TARGET="$(pwd -P)"`, as C4 Studio), never the git toplevel; the cookbook runs it from the directory the user names as the project root (default: the session's project root) and the first output line is `target <path>`. The runtime finds the same directory through `TSF_PROJECT`, which the mod exports (section 3, step 1), so a `tsf/` in a subfolder of a monorepo works.

**Report words.** One line per item, `<word> <path>`, fixed column: `stamped` = a file copied from `template/` (mod.just, permissions.json, .env.example, Start Here.md, layers/.gitkeep); `created` = a directory made (`tsf/`, `tsf/pages/`, `tsf/layers/`, `tsf/data/`) or a new `.gitignore` or root `justfile` written from nothing; `appended` = lines added to an existing `.gitignore` or root justfile; `kept` = already present (file, directory, ignore line, `mod tsf` or `mod? tsf` line, or a `tsf` recipe), left unchanged. A second run prints only `target` and `kept` lines. A new `.gitignore` is one line, `created .gitignore (tsf/.env, tsf/data/)`; a new root justfile is `created justfile (mod tsf)`. When something changed, an indented "Next steps" block follows (indented, so no line of it starts with a report word).

`tsf/mod.just` (meta-justfile mod template): header `# TSF: Tiny Software Factory, an Empty Factory with a durable agent (start, stop, restart, status, logs, push)`, `set shell := ["bash", "-cu"]` (bash, not zsh: a VM may not have zsh), `set positional-arguments`, `set working-directory := ".."`, `export TSF_PROJECT := parent_directory(source_directory())` (the folder that holds `tsf/`; `source_directory()` is the mod file's folder, just >= 1.27; `install.test.ts` asserts the value with `just --evaluate`), `skill := env("TSF_SKILL_DIR", "__SKILL_DIR__")` (the stamped absolute path is the laptop's; a clone elsewhere, such as a VM, sets `TSF_SKILL_DIR` instead of re-stamping, section 12), `own := source_directory() / "app" / "bin" / "tsf.mjs"`, `launcher := if path_exists(own) == "true" { own } else { skill + "/app/bin/tsf.mjs" }` (the project's copy when it has one, else the skill's) and `cli := 'node "' + launcher + '"'`, `[default] default: @just --list tsf`, and one-line recipes `start *ARGS`, `restart *ARGS` (`tsf restart`: POST /api/factory/restart on the running factory and wait for the new process; start it when none runs), `stop *ARGS` (so `just tsf stop --force` works), `status *ARGS` (with `[no-exit-message]`, so exit 3 "not running" prints no just error line), `logs *ARGS`, each `@{{cli}} <name> "$@"`, and `push *ARGS`, which runs `bash <skill>/scripts/push.sh "$@"`. `just --evaluate` run inside `tsf/` finds the root justfile, so `install.test.ts` evaluates the mod with `just --justfile tsf/mod.just --evaluate <var>`. No `_deps`: the launcher installs modules (one mechanism).

## 3. Runtime and startup sequence

Node 24+, ESM, TypeScript run by tsx; no server build (D12). `bin/tsf.mjs`:

1. **Install.** `installHash` = sha256 of `package.json` + `package-lock.json` (when present) + `process.version` major. When `node_modules/.tsf-install-hash` is missing or differs, it runs `npm install --no-audit --no-fund` (output to stderr) and writes the hash. So a changed `package.json` is installed again, not only a missing `tsx`.
2. Calls `register()` from `tsx/esm/api`, imports `src/main.ts` and exits with `runCli(argv)`. `start` imports `server/main.ts` and calls `runServer(opts)`.

`createFactory` runs steps 1-12 and `runServer` steps 13-15, in this order; each step logs one line; any failure exits 1 after releasing what it took:

1. Paths: `resolveProjectRoot(cwd)` = `TSF_PROJECT` (the mod exports it, section 2), else the nearest ancestor of cwd (cwd included) that holds `tsf/mod.just`, else `git rev-parse --show-toplevel`, else cwd. Require `tsf/` there (else "no tsf/ in <root>: run /tsf install"). Create `tsf/data/logs/`.
2. Env: `loadEnv(tsf/.env)`; never overrides a set, non-empty variable (section 12).
3. Lock: `lockFile(tsf/data/agent.sqlite.lock)` writes the pid with flag `wx`; a dead pid's lock is taken over; a live one fails with "already owned by process N" (D14).
4. App DB: `openAppDb(tsf/data/tsf.sqlite)` (no defaults argument): `DatabaseSync`, `PRAGMA journal_mode=WAL`, `synchronous=NORMAL`, `busy_timeout=5000`, `foreign_keys=ON`, migrations from `meta.schema_version`. The settings repository returns only stored keys (section 4.2).
5. Ceiling file: `readCeiling(tsf/permissions.json, --tools)`, called by `loadLayers` before it imports anything. Malformed JSON, a missing `allow`, or a pattern that is not a non-empty string fails startup (fail closed); a missing `deny` means none. Verdicts need the tool map, so the frozen `Ceiling` is built in step 6. `openFactoryAgent` then logs `ceiling.read` with the file's sha256, stores the hash under the raw settings key `ceilingSha256`, and logs a `ceiling.changed_on_disk` warning when it differs from the previous start (spec 2.5 detection, section 14).
6. Layers: discover, import, validate manifests, build the tool map, fail on a duplicate tool name, `buildCeiling`, filter tools by it, build extensions (section 8). The layer context's `settings()` and `ceiling()` getters are defined from here on: layer factories only capture them, and nothing calls them earlier (`ceiling()` throws `ServiceError("unavailable")` before the registry has loaded).
7. Models: `TSF_MODEL_PROVIDER=faux` installs the faux provider only; otherwise each enabled provider layer's provider (D1). Start the OpenRouter list refresh in the background (D2).
8. Harness: `Harness.open` on `openNodeSqliteStorage(tsf/data/agent.sqlite)` with one shared `RootedEnv` as `env`; `root()`; `main.configure()` from settings (model, thinking, extensions, tools, maxTurns, instructions, cwd). Nothing runs yet: no task runs before `resume()` or a submit.
9. Feed: `await feed.start()` opens the one watch (`main.watch(ctx, { min: 200, max: 400 })`), builds the initial view from `transcript.merge(watch.value)` (a watch never passes its value at attachment to the listener; the listener gets only later commits), then calls `watch.start(listener)`. Commits between acquisition and `start()` are queued by the watch, so no entry falls between the initial view and the first delta.
10. Service: `await createService(deps)` builds its own stores (section 9): `PageStore.init()` (mkdir, realpath, first scan) then `watch()`, focused page read, UI config load, theme CSS load, recorder (it reconciles from `feed.current()` and subscribes). On a fresh install (no stored `selection` key) it selects `Start Here.md` when that page exists (`by: "system"`), so acceptance 1 opens on it. `createFactory` then binds the late-bound `service()` getter of `OpenAgentOptions`.
11. Resume: `agent.resume()` starts auto-continue (section 7) and calls `harness.resume()`. Only now can a tool run, so a resumed page tool always finds the Service. Before binding, the getter throws `ServiceError("unavailable", "the factory is still starting")`, which no code path reaches.
12. Web (skipped with `--dev` and with `web: false`, which the in-process test factory sets): `WebHost.init()` (`ensureWebBuilt`, below) blocks before listen, so the URL line means the UI works, then `WebHost.watch()` starts the live rebuild. A failed first build logs the Vite error, and non-API GETs then answer 503 with a one-line HTML page naming the log file until a rebuild succeeds; the API still serves. The `WebHost` is created with the bus (step 4) and handed to the Service, so `rebuildWeb` and `status().web` see it.
13. HTTP: Hono on `@hono/node-server` `serve({ fetch, hostname: TSF_HOST, port: TSF_PORT })`.
14. State file: write `tsf/data/server.json` `{ pid, url, host, port, bootId, startedAt }` (atomicWrite), then print `TSF running at <url>` on stdout (the `start` recipe and the cookbook poll for it).
15. Start: `factory.start()` = `ServiceRuntime.start()` (section 9): `createService`'s runtime starts the `CronScheduler` (catch-up, then schedules), so cron starts after HTTP and `server/main.ts` stays as it was in P1.

**Web build (`server/static.ts`).** `webHash` = sha256 over the sorted relative paths and contents of `src/web/**`, `src/shared/**`, `vite.config.ts`, `package-lock.json`, first 12 hex chars. The output dir is `<app>/dist/web-<webHash>/`; it is fresh when it holds `index.html` and `.tsf-build` containing the hash. Otherwise: take `<app>/dist/.build.lock` (`wx`, pid inside, a dead pid's lock is taken over; a live one is waited on, polling 500 ms, up to 5 min), re-check freshness (another project's server may have built it), run `node node_modules/vite/bin/vite.js build --outDir <dir>.tmp-<pid> --emptyOutDir` as a child (stdout and stderr to the log), write `.tsf-build`, `rename` the tmp dir to the final dir, remove `dist/web-*` dirs of other hashes that are older than 10 minutes, release the lock. Two projects sharing the skill therefore build once and never see a half-written dir. When `<app>/dist` is not writable (a read-only skill dir), the same procedure runs under `<project>/tsf/data/web/`. `npm run build:web` (checks, `vite.config.ts` outDir `dist/web`) is separate and never served.

**Live web rebuild (`server/web-host.ts`, P9).** `WebHost` owns the directory the static handler serves (the handler asks for it on every request, so a swap never happens inside one). `rebuild()` runs `ensureWebBuilt` for the current sources: on success the served root and hash swap and `web.rebuilt { hash }` is published when the hash changed or the last build had failed; on failure the previous good build keeps serving, `lastError` holds vite's text (colour codes and stack frames dropped, the first 1500 characters) and `web.build_failed { error }` is published. Overlapping calls share one follow-up build, so an edit made during a build is built next. `watch()` uses `fs.watch(dir, { recursive: true })` on `<appDir>/src/web` and `<appDir>/src/shared` and rebuilds after 500 ms without events. `GET /api/status` carries `web: { hash, building, lastError }` (`hash` null when this process serves no built web: `--dev`, tests). The served `index.html` carries `<meta name="tsf-web-hash" content="<hash>">`; the client reloads (`location.reload()`) when `web.rebuilt` brings a different hash, and also when a snapshot after a reconnect (a restart) shows a different `status.web.hash`; under the dev proxy there is no meta tag and Vite's HMR does it. `web.build_failed` shows in a dismissible pw-ui `Alert` (`data-testid="web-build-error"`).

**Shutdown** on SIGINT/SIGTERM (force exit 1 after 5 s): `SseHub.closeAll()`, `server.closeAllConnections()` + close, `ServiceRuntime.close()` (cron first, then page watcher, recorder), feed `watch.stop()`, `harness.close(ctx)`, db close, remove `server.json`, unlock, exit 0. `harness.closed` resolving `{ kind: "failed" }` logs and exits 1 so systemd restarts. Only `runServer` (`server/main.ts`) handles this: it runs the same shutdown with exit code 1, so `server.json` and the lock are released. `ChatFeed.onFatal` (the feed gave up after more than 5 `listener_error` restarts in a minute, section 6) takes the same path: `runServer` subscribes and shuts down with exit 1. Neither `openFactoryAgent` nor the feed exits the process itself, so an in-process test factory is not killed by a failed Harness or feed.

**Restart (`factory.restart`, P9).** `Service.restart({ reason? }, origin)` answers `{ restartingInMs: 1500, mode }` at once, publishes `factory.restarting { inMs, reason?, by }` (the web shows "Restarting" in the connection badge until the next snapshot, and its event stream reconnects by itself) and, 1.5 s later, calls the hook `runServer` supplied; without a hook (the in-process test factory, anything not started by `tsf start`) it answers `conflict`. The hook runs the shutdown above, then: **under a supervisor** (`INVOCATION_ID` or `TSF_SUPERVISED` set; the generated unit sets `TSF_SUPERVISED=1`) exit code 3, which `Restart=on-failure` restarts (`Restart=on-failure` restarts on any non-zero exit; systemd.ts keeps it); **otherwise** it releases the lock and closes the listener (the full `close()`), spawns a detached replacement (same `process.execPath`, `execArgv`, `argv.slice(1)`, cwd and environment; stdout and stderr appended to `tsf/data/logs/tsf.log`) and exits 0. Calls during the delay do not schedule a second restart. A turn in flight is interrupted by the shutdown like any stop and continued by auto-continue (section 7) in the new process; the one `continue` is keyed by the interrupted run's task id. **No loop:** an agent call's id is stored in the app database (`settings` key `restart.last_call`) before the process exits, so a `restart_factory` call that runs again (replay `safe`) answers `{ restartingInMs: 0, alreadyRestarted: true }` and restarts nothing; the tool call is also recorded as done within milliseconds of the reply, 1.5 s before the exit. `tests/integration/liquid-core.test.ts` proves both modes under the real launcher.

**CLI commands other than start** run in a separate process with the same step 1 (no env, lock or db), except that a missing `tsf/` does not fail them with exit 1: `status` then prints `not running (no tsf/ in <root>: run /tsf install)` and exits 3. `stop` reads `tsf/data/server.json` (falling back to the lock pid), sends SIGTERM to that pid when it is alive and waits up to 10 s for the lock file to disappear (then reports `stopped`; still alive: exit 1 with "still running"); with no live pid it prints `not running`, exits 0 and removes a stale `server.json`. With a systemd unit installed (section 12) it prints that `systemctl` owns the process and runs nothing unless `--force`. `status` reads `server.json` and checks the pid: no file or a dead pid prints `not running` (exit 3); a live lock pid with no `server.json` prints `starting (pid N)` (exit 0); a live pid whose server does not answer exits 1; otherwise `GET <url>/api/status` (2 s timeout) prints name, url, model (`provider/modelId`), busy (`--json` prints `{ running, url, status }` raw). `start` validates `--port` as an integer 0..65535 (exit 2 otherwise); `--tools` absent gives `null`, given (even empty) a string array; `runCli(["start", ...])` never resolves while the server runs (the listening socket and `runServer`'s signal handlers own the process). The CLI finds the server URL only in `tsf/data/server.json`, never from `.env`, `TSF_PORT` or `--port` (the lock file gives only a pid). `logs` tails `tsf/data/logs/tsf.log` (`-f`, `-n N`). The systemd unit is written by `scripts/vm-tsf.sh` on a VM, not by the CLI (section 12). Exit codes: 0 ok, 1 failure, 2 usage, 3 `status` when not running.

Defaults: `TSF_HOST=127.0.0.1`, `TSF_PORT=8000` (the exe.dev proxy forwards 8000 to `https://<vm>.exe.xyz` with no port). `server.json.url` uses `127.0.0.1` when the host is `0.0.0.0`. `--dev` proxies non-`/api` requests to `TSF_VITE_URL` (default `http://127.0.0.1:5173`, started by `npm run dev:web`) through global fetch; Vite HMR connects to Vite directly (`server.hmr.clientPort`). `staticHandler` and `devProxy` both inline the theme into HTML responses (section 11, Theme).

## 4. Data model

### 4.1 `tsf/data/agent.sqlite`

pi-durable's storage (schema version 2, migrated automatically from 1.4.0+). Never opened by app code. Holds the root conversation (`ROOT_CONVERSATION_ID`), entries, tasks, submissions and documents: `pi.agent`, `pi.live`, `pi.inbox`, `pi.usage`, `pi.provider`, and TSF's `tsf.prompt-sections` (P5, D6). Custom entry kind: `tsf.cron` (`CRON_ENTRY_KIND`, P6): a cron fire is `submit({ type: "input", content: prompt, requestId, whenBusy: "followUp", entry: { kind: "tsf.cron", data: CronEntryData } })`; pi-durable places it as a `tsf.cron` entry whose `model` is the user message and `data` the `CronEntryData` (`{ cronId, name, slot, catchUp, manual }`), and the waiting `pi.inbox` item carries the same `entry` (probed on 1.5.0). That is how chat-view, the inbox view and the recorder recognise cron. Request id namespaces: `chat:<uuid>`, `cron:<cronId>:<slot>`, `cron-now:<cronId>:<callId|uuid>`, `continue:<taskId>`.

Migrations: migration N belongs to phase N and is added by the lot that owns `db.ts` in that phase (1: `meta`, `settings`, `model_cache`; 2: `runs`, `run_tools`; 3: `ui_config`; 4: `themes`; 5: `custom_prompts`, `runtime_prompts`; 6: `crons`, `cron_runs`; P7 and P8 add none, so the schema version is 6). Each runs once in a transaction and sets `meta.schema_version = N`; `migrate(version, sql)` is a no-op for an applied version. `AppDb.runs` (`RunsRepo`: `save(run, tools)` in one transaction, `list`, `get`, `row`, `running()`, `byFirstEntry(first)`) arrives with migration 2. `trigger` is quoted in SQL (a keyword). Stored raw keys beyond `StoredSettings`: `selection` and `ceilingSha256` (through `getRaw`/`setRaw`).

**Settings: stored keys and defaults (`core/settings.ts`).** The `settings` table holds only keys that were written; nothing is stored at first start, so no defaults are needed to open the db. Stored keys: every `Settings` field except `layersEnabled`, plus the non-config keys `selection` (`Selection` JSON) and `layerToggles` (`{ [layer]: boolean }`, written by `setLayerEnabled`). `settingsDefaults(projectRoot, manifests)` gives `factoryName` = `basename(projectRoot)`, `toolsDisabled` = [], `model` = null (first model of the active provider; the OpenRouter default is `{ provider: "openrouter", modelId: "anthropic/claude-sonnet-5.5" }`), `thinkingLevel` = "low", `compaction` = `DEFAULT_COMPACTION_POINTS` (200k / 500k), `systemPrompt` = null, `maxTurns` = 60. `mergeSettings(defaults, stored, manifests)` lays the stored keys over the defaults and derives `layersEnabled` = loaded layers in load order where `layerToggles[name] ?? manifest.enabledByDefault` is true, plus every `required` layer. The manifests come from the registry, so `FactoryAgent.settings()` (section 7) is the one getter: it is defined once step 6 has loaded the layers, caches the merged value, and the cache is dropped by every `SettingsRepo.set`. A layer added later is enabled by its own default; a toggle the user made sticks.

**Mutexes (spec 11).** `KeyedMutex` keys, one per resource, in lock order: `pages` (every page and folder write, selection), `settings` (model, thinking, compaction, system prompt, `layerToggles`, `toolsDisabled`, `maxTurns`), `themes`, `ui_config`, `prompts` (custom and runtime prompts, section toggles), `cron`, `layers` (P9: every change to a layer folder and the registry reload; `MUTEX_ORDER` in `core/mutex.ts`), then `layer:<name>`. The methods that change a layer folder take `layers` alone, then, after releasing it, `settings` (drop a deleted layer's toggle) and `ui_config` (placements and hotkeys of the changed layers). A method that touches two resources takes them in this order and never the reverse: `selectPage` takes `pages` then `ui_config`, a theme change `themes` then `ui_config`.

### 4.3 Pages

Markdown files under `tsf/pages/`, nested folders. Path rules (`core/pages.ts`): POSIX, relative, no empty, `.` or `..` segment, no segment starting with `.`, no `\` or NUL, at most 8 levels, segment at most 120 chars; a page path ends in `.md` (appended when missing on create; `move_page`/`delete_page` also find `Notes/Hello.md` when given `Notes/Hello`); a folder name cannot end in `.md`; a page over 1 MB is `too_large`; the resolved real path must stay inside `tsf/pages` (a symlink leading out is refused). The tree and the rescan skip symlinks, dot names and non-`.md` files. Writes are `atomicWrite`. One `pages` mutex serialises every page write (spec 11): the Service holds it across the store write, the selection/focus change and the event, so `PageStore`'s write methods (`create`, `update`, `move`, `remove`, `mkdir`) do not take it themselves; only the debounced rescan does. `PageStore` also has `init()` (mkdir, realpath, first scan with no callback, called by the Service before `watch()`), `rescan()`, `hasFolder()`, `hasPage()` and an optional `debounceMs` (default 150). `fs.watch(pagesDir, { recursive: true })`, debounced 150 ms, rescans and publishes `pages.changed` and `page.updated` for files changed outside the Service (the user's editor, coding_tools `write`). `Page.version` = first 12 hex chars of sha256(content).

**Own writes versus external ones.** `PageStore` keeps `known: Map<PagePath, { version, size, mtimeMs }>` and the in-memory tree. Every Service write, move, delete and mkdir updates `known` and the tree inside the `pages` mutex before it returns, so the fs event it causes finds nothing new. The rescan also runs under the `pages` mutex: it lists the files, re-hashes only those whose `size` or `mtimeMs` differ from `known`, and reports `changed` = paths whose hash differs or that are new, `removed` = known paths now missing. Only when either is non-empty, or a folder appeared or disappeared, does it update `known` and the tree and call `onExternalChange(changed, removed, { structureChanged })` (it may return a promise, awaited inside the mutex), which publishes `pages.changed` when `structureChanged` (the path set changed, folders included), `page.updated` per changed page and `page.removed` per removed page, all `by: "system"`. A Service write therefore publishes its events exactly once; `api-pages.test.ts` asserts this.

**In-memory page state (for the synchronous snapshot).** `PageStore.tree()` is the in-memory tree, rebuilt by each scan. The Service keeps `focus: Page | null`, the selected page's content, and changes it only inside the `pages` mutex, assigning it and publishing the event in the same synchronous step after the awaited read or write:
- `selectPage`: read the page, set selection and `focus`, publish `selection.changed { selection, focus }`.
- a Service write whose path is the selected one: `focus` = the returned `Page`, publish `page.updated`.
- `onExternalChange(changed, removed, info)` (called while the rescan holds the `pages` mutex, so it must not take it again): when the selected path is in `changed`, re-read it, set `focus`, publish `page.updated`; when it is in `removed`, clear the selection (`by: "system"`), set `focus = null`, publish `selection.changed`.
- `movePage` / `deletePage`: selection follows or clears, as in the section 9 table; that `selection.changed` carries the origin's actor (`ui` or `agent`). External removal and boot clearing use `system`. `unselectPage` with nothing selected and `createFolder` of an existing folder publish nothing.
- boot (`createService`): read the stored selection's page; a missing file clears the selection.
`snapshot()` reads `tree()`, `selection` and `focus` with no await. A snapshot taken while a write is in flight shows the old content and is followed by the `page.updated` delta, whose id is larger than the snapshot's head, so the client converges.

### 4.4 UI config

One document, `UiConfig` in `shared/types.ts`, default `DEFAULT_UI_CONFIG`. Writes take a JSON Merge Patch (objects merge, arrays replace, `null` deletes), validate the merged result with the compiled schema, set `version = old + 1`, store, publish `ui_config.changed`. A `baseVersion` that is not current is `conflict` (409). JSON Schema outline (`shared/ui-config-schema.ts`, built with pi-schema `obj`/`str`/`int`/`bool`/`arr`/`oneOf`/`map`, closed objects; `oneOf(a, b)` below is shorthand for pi-schema's one-array form `oneOf(["a", "b"])`):

```
UiConfig { version: int>=1,
  panes: { left: Pane, right: Pane, agentMaximised: bool },   Pane { visible: bool, width: int 160..960 }
  navbars: { global: Navbar, agent: Navbar },                 Navbar { visible: bool, items: arr(Placement, max 24) }
    Placement { id: str pattern ^[a-z0-9_.-]{1,64}$ (unique across navbars), widget: str (built-in or "<layer>.<widget>"),
                slot: oneOf(left, center, right), options: obj({ fullWidth: opt(bool) }, { open: true }) }
  theme: { name: str 1..64, mode: oneOf(light, dark, system) }   -- written only through setTheme (P4), so the CSS follows
  hotkeys: map(str 1..16)   -- keys: HotkeyAction or "<layer>.<action>"; values: one key or "mod+key"; no duplicates
  animations: { agentWorking: oneOf(pulse, glow, spinner, none), agentIdle: oneOf(still, breathe), reducedMotion: oneOf(system, on, off) } }
```

Semantic checks after the schema (`checkUiConfig(doc, { widgets?, themes? })`): unique placement ids, known widget types for each navbar (`WidgetContribution.navbars`; the Service passes the layers' widget contributions), known theme name (from P4, when a theme list exists; P3 passes no list and skips it), every built-in `HotkeyAction` keeps a key, a key value is one key or `mod+key`, and no two actions on one key (compared case-insensitively). A patch that contains `theme` through `updateUiConfig` is `invalid` ("use set_theme") even when the value would not change, so every theme change goes through `setTheme`, which also publishes `theme.applied`; a `version` key or a non-object patch is `invalid` too. A patch that changes nothing returns the current document with no version bump and no event. `UiConfigStore` keeps the document cached in memory; on load the stored document is laid over the defaults, and if it no longer validates the defaults are used at the stored version. `ui-config-schema.ts` also exports `PANE_MIN_WIDTH`, `PANE_MAX_WIDTH`, `NAVBAR_MAX_ITEMS` and `HOTKEY_ACTIONS`.

**Request guard** (`server/guard.ts`, before `bodyLimit` on `/api/*`; there is no in-app auth, so a page the user visits must not drive the factory): (1) the Host name must be `localhost`, `*.localhost`, an IP literal, the listen host, or a name in `TSF_ALLOWED_HOSTS` (comma-separated), else 403 `forbidden` naming the variable (DNS rebinding); (2) an `Origin` header, when sent, must equal the request's host or name an allowed extra host (`null` is refused), else 403 `forbidden` (cross-site requests); (3) every method other than GET, HEAD and OPTIONS needs `content-type: application/json`, else 415 `invalid`, bodiless commands (`/chat/stop`, `/pages/unselect`) included, so a cross-site form post or `no-cors` fetch (a simple request, no preflight) never reaches a command, and a cross-origin JSON request needs a preflight the API never answers with CORS headers. ## 6. SSE protocol (D9)

One stream, `GET /api/events`, a `ReadableStream` Response with `content-type: text/event-stream; charset=utf-8`, `cache-control: no-cache, no-transform`, `connection: keep-alive`, `x-accel-buffering: no`, first line `retry: 2000`. Every message is `event: <frame.type>` plus `data: <JSON of the SseFrame>` (the frame repeats its `type`, so it is self-describing in logs).

- **Ids.** One process-wide counter, starting at `bootId * 1000` where `bootId = Date.now()` at startup, incremented per delta. A later process always issues larger ids, so a stale `Last-Event-ID` can never match a new process's ring. `snapshot` frames carry `id: <head>` (the id of the newest delta folded into it); `delta` frames carry their own id; `hello` and `ping` carry none, so they never move the browser's `lastEventId`.
- **Order on connect.** `hello { apiVersion, bootId, serverTime, resumed }`, then either the missed deltas (`resumed: true`) or one `snapshot` (`resumed: false`), then live deltas.
- **Resume.** The hub keeps a ring of the last 500 delta frames. With `Last-Event-ID: n` (EventSource sends it on its own reconnects; `?lastEventId=n` for curl and tests): if `n === head`, nothing is replayed; if the ring holds `n + 1 .. head`, those are replayed; otherwise (miss, other boot, page refresh with no id) a fresh snapshot is sent.
- **Snapshot.** `Service.snapshot()` is synchronous over in-memory state (feed view, page tree, selection and focused page, settings, UI config, layers, tools, ceiling, newest 20 runs, themes, cron), taken in the same tick as `head`, so snapshot plus later deltas is exact. The focused page comes from the Service's `focus` cache (section 4.3), never from an async read.
- **Deltas.** `Delta = ChatDelta | AppEvent`. Chat deltas come from the feed (one watch per process, not per connection); app events come from the bus. The hub assigns the id, appends to the ring and writes to every open stream.
- **Ping.** `event: ping`, `data: {"type":"ping","serverTime":...}` every 15 s per stream.
- **Backpressure.** The stream uses a `ByteLengthQueuingStrategy({ highWaterMark: 2_000_000 })`; when `controller.desiredSize <= 0` the hub closes that stream and the browser reconnects (resume or snapshot).
- **Close.** Client disconnect (`c.req.raw.signal` abort) removes the stream. Closing a stream never aborts work. `closeAll()` on shutdown; new streams get 503 while closing.

Feed to deltas (`agent/feed.ts`): the watch is opened with `{ min: 200, max: 400 }` (the default window is 50 to 100). The initial view comes from `transcript.merge(watch.value)` before `watch.start()` (section 3, step 9; pi-durable README "Watching a Conversation"). On each later `WatchCall` of kind `value`, `transcript.merge(call.value)` gives a `TranscriptView`; entries not seen before become `chat.append` items; tool items whose result entry arrived become `chat.update`; `pi.live` + `pi.inbox` changes become one `chat.live` (whole `ChatLive`, compared by JSON); `pi.agent` + `pi.usage` changes become `chat.meta`. Only a watch root replacement (`ops[0][0] === "r"`, or chord/delta `isReplace`/`isBase`) sends `chat.reset`. Entry ids have holes (task ids share their id space; a `ping` turn gave entries 7, 10), so nothing infers missed entries from ids: missed entries show up only as transcript `gap` items. The feed keeps the newest 200 items; older ones are paged with `Conversation.entries`. Every value is also handed raw to `onCommit` listeners as a `FeedCommit { value: ConversationView; added: readonly EntryRecord[]; at: number }` (`at` = `Date.now()` on delivery), and `current()` returns the newest one; the recorder reads these (section 7).

API shapes the feed handles explicitly:
- `TranscriptView.items` holds `{ kind: "entry" }`, `{ kind: "gap", after, upTo }` and `{ kind: "earlier" }`. The feed calls `transcript.fillGap(...)` for every gap before emitting (a gap means entries were skipped between two watch values), then emits the filled entries as `chat.append` in id order; while a gap is being filled, later values queue behind it (one promise chain). `earlier` sets `ChatView.hasEarlier = true`; the feed never calls `loadEarlier` itself (the client pages with `GET /api/chat/earlier`).
- A Durable watch never sends a `WatchCall` of kind `failed` (its failures are final); the listener ignores any non-`value` call.
- `WatchHandle.closed` resolving `stopped` (our `stop()`) or `aborted` is a normal end. `ended` (session closed) is normal during shutdown. `failed` means the Harness failed and is closing itself: the feed does not reopen, it logs and leaves exit to the `harness.closed` path (`{ kind: "failed" }` exits 1, section 3). Only `listener_error` is restarted: log, open a new watch with the same window, build the view from its `watch.value`, and send `chat.reset` with it (at most 5 restarts per minute; past that the feed stops and calls its `onFatal(fn)` listeners once, and `runServer` shuts down gracefully with exit 1, section 3; the feed never calls `process.exit`). The listener catches its own errors (a throwing listener ends the watch) and logs them.

**Main conversation and submit.** The root is the factory's conversation (`ROOT_CONVERSATION_ID`). A chat POST awaits `submit()` (admission is committed) and `status()`, then returns 202. The run continues in-process; output reaches clients only through the feed.

**Busy and queueing.** `whenBusy` defaults to follow-up: a message sent during a run is placed when the run answers (`pi.inbox`, shown in `ChatLive.inbox`). Cron fires use the same, which is spec 8.6's queueing.

**Settings to configure.** `applyAgentSettings()` builds one `AgentChange` from settings and the registry, every time in full (a given field replaces the stored one):

- `model`: the effective `ModelRef` (settings.model if the active catalog has it, else the catalog default); `thinkingLevel: clampThinkingLevel(model, settings.thinkingLevel)` (pi-ai `clampThinkingLevel<TApi>(model: Model<TApi>, level: ModelThinkingLevel): ModelThinkingLevel`).
- `extensions: { add, remove }` against the host default (`settings.extensions` getter): `add` = enabled layers not enabled by default, `remove` = default layers the user disabled; `null` when both are empty. It is always recomputed whole, so the "a second edit replaces the first" behaviour never drops a toggle. `remove` never contains a required layer (D7).
- `tools: toolsDisabled.length ? { remove: [tool objects] } : null`. Tools outside the ceiling are not registered, so they cannot be named.
- `maxTurns`, `instructions` (runtime prompts, P5), `cwd: projectRoot`.

**Compaction mapping (D3).** `toPolicy(window, points)` (port of the reference `compaction.ts`, constants 200k/500k): `forced' = max(0, min(points.forced, window - 16_384))`; `reserveTokens = window - forced'`; when `points.background >= points.forced` background compaction is off (`background' = null`, `backgroundTokens = 0`; the formula alone would give 8 192); otherwise `background' = min(points.background, forced' - 8_192)` and `backgroundTokens = background' >= 4_096 ? forced' - background' : 0`; `enabled` and `keepRecentTokens` pass through. Stored points stay absolute; the clamp happens at read time for the current model's window, so a model change clamps both thresholds with no write (`EffectiveCompaction.clamped`). The settings getter reads the current window from the catalog for the root's model.

**Hooks.** One hook registration: the ceiling guard `hook(ToolTask, { beforeTool, afterTool })` in `factory_harness` (section 8). Signatures: `beforeTool(call: ToolHookCall, api: HookApi, context: Context): HookResult<{ readonly arguments?: JsonObject; readonly block?: string }>` (first block wins; a throw blocks; it runs only for a call whose tool resolved), `afterTool(call, result: ToolExecutionResult, api, context): HookResult<ToolExecutionResult>` (runs on every result the tool task writes, including the Harness's own `tool_unavailable`, `invalid_arguments` and `blocked` results; returning a result replaces it). No logging hooks: the recorder reads committed state from the feed, because hooks rerun on replay and stop running after `restartLimit`.

**Prompt sections.** `section(key: string, render: PromptSection["render"], options?: { tag?: boolean })`. Keys are namespaced `<layer>-<key>`: pi-durable 1.5.0 `registry.install` requires section keys to match `/^[a-z][a-z0-9_-]*$/` (`dist/harness/registry.js`, `SECTION_KEY`), so a dot is rejected; layer names contain no `-`, so the first `-` separates layer from key (`registry.ts` exports `sectionPrefix(layer)`). `instructions` is reserved. factory_harness renders `factory_harness-system` (override or `system-prompt.md` with `{{factoryName}}`, `{{projectRoot}}`, `tag: false`) and `factory_harness-identity` (stable text, no clock: sections that change every request defeat the prompt cache).

**Tools, memo and tasks (D13).** Every TSF tool is built with `defineAppTool`, which requires `replay` and wraps pi-durable `defineTool<TParameters extends object, TDetails extends JsonValue>(tool: ToolRegistration<TParameters, TDetails>)`. Parameters use pi-schema builders (`obj`, `str`, `int`, `bool`, `arr`, `opt`, `oneOf`; objects closed by default). Results: `{ output: [{ type: "text", text: JSON.stringify(result) }], details: result }`; a `ServiceError` becomes `{ isError: true, output: [...] }` so the model can fix its call; any other throw is re-thrown and pi-durable gives the model its own error result. Exactly-once helpers: `once(api, key, ctx, fn)` over `memo<T>(name, ctx): Promise<T | undefined>` and `memo<T>(name, candidate: T, ctx): Promise<T>`; `onceInCommit` with a task-scoped receipt doc (`checkpointWhen: () => false`). Rules:

| Tool kind | replay | Mechanism |
|---|---|---|
| reads (`list_*`, `read_page`, `get_*`, `describe_tool`, `check_theme`, `refresh_models`) | safe | none needed (`refresh_models` re-fetches a public list; repeating it is harmless) |
| idempotent sets (`select_page`, `unselect_page`, `set_*`, `toggle_prompt`, `set_tool_enabled`, `set_layer_enabled`, `update_ui_config`, `remove_runtime_prompt`, `clear_runtime_prompts`, `open_panel`) | safe | the same input yields the same state (`open_panel` re-opening a modal on replay is harmless) |
| creates keyed by the call (`create_custom_prompt`, `append_runtime_prompt`, `create_cron`, `create_theme`) | safe | row id derived from `api.callId` with `INSERT ... ON CONFLICT DO NOTHING` |
| `run_cron_now` | safe | requestId `cron-now:<cronId>:<callId>`: pi-durable dedupes the submission |
| `jev_judge` | safe | verdict stored with `api.memo("verdict", ...)` before it is returned |
| page writes (`create_page`, `update_page`, `move_page`, `delete_page`, `create_folder`) | unsafe | atomic file ops; a crash mid-call gives the model an `interrupted` result, never a second write |
| `compact`, `fix_theme`, `delete_*` (incl. `delete_custom_prompt`) | unsafe | at most once |
| layer tools over `layerAction` | as the layer declares | the layer's handler declares `replay`; `defineAppTool` still requires it |
| `read`, `write`, `edit`, `bash` (pi-durable/tools) | unsafe | at most once; they are not built by `defineAppTool` (which wraps a `run()`), so `coding_tools/extension.ts` re-states each as `{ ...createXTool(), replay: "unsafe" }` to declare `replay` explicitly |

**Faux model (D1).** `fauxProvider(options?: RegisterFauxProviderOptions): FauxProviderHandle` with `{ provider: "faux", models: [{ id: "faux-1", reasoning: true, contextWindow: 1_000_000, maxTokens: 64_000 }], tokensPerSecond: Number(TSF_FAUX_TPS ?? 200) }`. `reasoning: true` alone gives `off`..`high` (`getSupportedThinkingLevels` adds `xhigh` and `max` only when `model.thinkingLevelMap[level] !== undefined`, and `FauxModelDefinition` has no such field), so `installFaux` sets `handle.models[0].thinkingLevelMap = { xhigh: "xhigh", max: "max" }` after `fauxProvider()` and before `catalog.models.setProvider(handle.provider)`; then all seven levels are supported and `clampThinkingLevel(m, "max")` is `"max"` (verified on pi-ai 1.5.0; `faux.test.ts` asserts it, and acceptance 5 depends on it). One response factory (`FauxResponseStep` function form `(context: TranscriptContext, options, state, model) => AssistantMessage`) re-appends itself with `appendResponses` and answers from rules: a rule matches on the turn (last user text, tool results since it, offered tools) and returns text (`fauxText`) or tool calls (`fauxToolCall(name, args)`, `fauxAssistantMessage(content, { stopReason: "toolUse" })`). Rules are pure functions of the transcript, so a regenerated request after a crash answers the same; faux tool-call ids are derived from a hash of the transcript for the same reason. Four copies of the response factory are kept queued, so concurrent requests never hit "No more faux responses queued". With faux on, `createModelCatalog` returns an empty catalog (`source: "faux"`) and `openFactoryAgent` calls `installFaux` with `testing.rules` followed by `loadFauxRules()`. Built-in rules: `ping` → `pong`; `long turn` → a 2 000-token answer (10 s at 200 tok/s); `effect turn` (P2) → `bash` `echo effect >> tsf/data/effects.log; sleep 6`, then `effect turn done`; `probe <tool> [<json>]` (P2) → one call to `<tool>` with the JSON object after the name as arguments (default `{}`), whether or not the tool is offered, then `probe done`; the test supplies arguments that fit the schema when the tool is registered (an unoffered call is never validated); fallback echo. `TSF_FAUX_RULES=<module path>` adds rules (`export const rules: FauxRule[]`) ahead of the built-ins (demo, tests).

**Auto-continue.** When `ChatLive.runFailure.reason === "interrupted"` (the generation's retries ran out across crashes) and the conversation is idle, `agent/continue.ts` submits `{ type: "continue", requestId: "continue:<runTaskId>" }` once; `ConversationBusy` is ignored. `restart_limit` is not continued (crash loop); it shows in the agent pane. It is started by `FactoryAgent.resume()`, because a submit also starts the scheduler.

**Recorder (`agent/recorder.ts`, T2).** Input: `feed.onCommit` and, at start, `feed.current()` (section 6), never `ChatItem`s. A run is the span in which `docs["pi.live"].run` is present; `id` = the first `run.taskId` seen, `first_entry` = `run.first`. On start the recorder matches an open run by `first_entry` and pages its entries with `main.entries({ minEntryId: first, order: "ascending" }, 200, cursor, ctx)`, so a restart neither duplicates nor loses rows. Fields: `trigger` from the first entry: kind `tsf.cron` → `cron`; `pi.user` whose `first` already belongs to a finished recorded run → `continue` (a continue keeps the failed run's `first`); `pi.user` → `chat`; else `system`. `startedAt` = the first entry's message `timestamp`, else the `FeedCommit.at` the run appeared; a `continue` run always uses the `FeedCommit.at` (its `first` is the failed run's, whose timestamp would stretch the duration across the interruption); `finishedAt` = the `at` it disappeared. `status`: `pi.live.runFailure` set by that end → `aborted` when its reason is `aborted`, else `failed` (`failure` = reason); otherwise `answered`. `turns` = the last `run.turns` seen; `toolCalls`, `usage`, `model` from the run's `pi.assistant` entries (id ≥ `first` and `byTaskId` ≥ the run id: the run's `taskId` changes from one generation to the next, 9 to 14 in a probe, and tool tasks take ids in between, so attribution uses ascending ids, which also needs no in-memory task set after a restart): usage summed, `costSource` = `provider` only when every one has `usage.cost.totalFromProvider`, `model` = newest `provider/model`. `run_tools` rows from each tool call and its `pi.tool-result` entry (status by chat-view's `resultStatus`; a call with no result is `pending`/`running` while the run is live and `interrupted` once it ends). `failure` holds the `runFailure` reason only. `prompt` = the first entry's text, 300 chars. Commits are processed one at a time through a promise chain; rows are written only when the derived content changes; a follow-up run placed in the commit that ends the previous one is split at the new `first`; a row still `running` with no matching live run is closed at boot; `stop()` leaves an open row `running` for the next recorder. `run.recorded` is published once, when a run ends.

**Shutdown.** `close()` seals admission, settles commits and writes running tasks back as pending, uncounted ("a close is not a crash").

**`openFactoryAgent` contract (final from P1; later phases change the body, never the signature).** `OpenAgentOptions { paths; log; bus; db: AppDb; service: () => FactoryService; tools: readonly string[] | null; testing?: { skipCeilingFilter?: boolean; rules?: readonly FauxRule[] } }`. `FactoryAgent { harness; main: Conversation; catalog: ModelCatalog; registry: LayerRegistry; feed: ChatFeed; settings(): Settings; applySettings(): Promise<void>; resume(): void; close(): Promise<void> }`. It runs steps 5 to 9 of section 3 in that order and never resumes; `createFactory` calls `resume()` (auto-continue, then `harness.resume()`) after `createService` (step 11). `loadLayers(opts: { ctx: LayerContext; builtinDir: string; projectDir: string; cliTools: readonly string[] | null; testing?: { skipCeilingFilter?: boolean } }): Promise<LayerRegistry>` has this signature from P1; the P2 body loads the built-ins that exist (section 8), then `tsf/layers/*`, reads and applies the ceiling, and honours `testing.skipCeilingFilter`. P2 adds to `LayerRegistry`: `ceiling(): Ceiling`, `extension(name)`, `selection(settings): { add; remove }`, `toolObjects(names)`; `LoadedLayer` gains `defined` and `outsideCeiling`; `FailedLayer` and `BUILTIN_LAYERS` are exported.

## 8. Layers

**Contract (D5).** `layers/<name>/manifest.ts` exports `manifest: LayerManifest` (`shared/types.ts`). `layers/<name>/extension.ts` exports `createExtension(ctx: LayerContext): Extension`, provider layers also `createProvider(ctx: LayerContext): ProviderLayer`, and a layer with its own state may export `createHandlers(ctx: LayerContext): LayerHandlers` (below, P4). A factory rather than a constant, because tools close over the Service. `LayerContext` (`agent/layer-context.ts`): `{ service: () => FactoryService, paths, log, bus, settings: () => Settings, ceiling: () => CeilingView, modelCache, jev: (input: JevInput, ctx: Context) => Promise<JevVerdict>, pi: PiKit }`. Three members are getters because their value exists only after the factories ran: `service` (bound after `createService`, before `resume()`, section 3), `settings` and `ceiling` (both defined at the end of step 6; `ceiling()` returns the registry's frozen `Ceiling`, `ALLOW_ALL` in P1, so the guard reads the real one with no swap). Factories only capture them; tools and hooks call them at execute time. `jev` is the spec 7.4 helper "available to all layer code", the same function `Service.jevJudge` and the `jev_judge` tool call, wired in P7 and throwing `ServiceError("unavailable")` before; `JevInput`, `JevVerdict` are in `shared/types.ts`; `PiKit` re-exports `defineExtension`, `defineTool`, `section`, `hook`, `wrapSection`, `ToolTask`, `defineAppTool`, `toolOk`, `toolErr` and the pi-schema builders, so project layers need only `import type` (erased by tsx) and resolve no packages from the host project. `ProviderLayer = { provider: Provider; refresh(signal: AbortSignal): Promise<void>; models(): ModelInfo[] }`.

**Registry (`agent/registry.ts`).**
1. Discover: built-ins in fixed order `factory_harness`, `provider_openrouter`, `coding_tools`, `page_harness`, `factory_controls`; then `tsf/layers/*/` sorted by folder name. This is load order = install order = section order = host default order.
2. Import each `manifest.ts` and `extension.ts` with `import(pathToFileURL(file).href)` (a project layer from a fresh copy of its folder, see Reload below). A built-in folder that does not exist is skipped (all five exist now); a built-in that exists and fails is fatal; a project layer that fails is recorded (`status: "failed"`, `error`, named after its folder, in discovery order in `infos()`) and skipped.
3. Validate: `manifest.name` equals the folder name and is `^[a-z][a-z0-9_]{1,40}$`; unique across built-in and project layers; the extension's `name` equals it; section keys start with `<name>-` (section 7, Prompt sections); widget ids `<name>.*`.
4. Tool map: `Map<toolName, layerName>` over every extension's `tools`. A tool name defined by two layers fails startup naming both (D8). Names must match `^[a-z][a-z0-9_]{0,63}$`.
5. Ceiling filter: each extension is rebuilt as `defineExtension({ ...ext, tools: ext.tools.filter(t => ceiling.allows(layer, t.name)) })` before `registry.install`. Excluded tools appear in `LayerInfo.toolsOutsideCeiling` and `CeilingInfo.denied`, nowhere else. Under `testing.skipCeilingFilter` they are registered, but `toolInfos()` and `LayerInfo.tools` still leave them out (`ToolInfo.inCeiling` is the literal `true`). A layer that defines tools but keeps none (`coding_tools` under `deny: ["coding_tools.*"]`) is rebuilt with `sections: []` too, so its prompt section never describes tools the model lacks; layers without tools by design (factory_harness, providers) keep theirs.
6. Selection: `defaultSelection` = extensions of layers with `enabledByDefault`; runtime state = `settings.layersEnabled` applied with `configure` (section 7).

**Enable or disable (P5 tools, Service in P2).** `setLayerEnabled(name, enabled)` writes `layerToggles[name]`, re-applies the agent, publishes `layers.changed` and `tools.changed`. It refuses (`forbidden`) to disable a `required` layer. A provider layer's disable calls `catalog.deleteProvider(id)` (`MutableModels.deleteProvider(id: string): void`) and enable calls `setProvider(provider: Provider): void`; under faux, provider layers do not touch the catalog. A new layer folder is picked up on restart, or at once by `reload_layers` and the authoring tools, with its `enabledByDefault` (section 4.2). Edge cases:
- **Last provider.** Outside faux, disabling the last enabled provider layer is `conflict` ("at least one provider layer must stay enabled: no model would remain"). Under faux the check is skipped (faux is always the model).
- **factory_controls.** Not required. The agent may disable it (or `set_tool_enabled` / `set_layer_enabled` themselves) and then cannot re-enable anything; the UI always can, because UI controls call the Service directly. The tool's result says so ("the UI can re-enable it"). factory_harness alone is required, as D7 says.
- **Model gone.** When the stored model's provider is disabled or the model leaves the live list, `applyAgentSettings` falls back to the catalog default and `ChatMeta.model` shows it; the stored `model` stays, so re-enabling restores it.
- **Missing `tsf/layers/`.** Treated as empty (install stamps `layers/.gitkeep` so a fresh clone has it).

**Layer handlers and UI (D5, P4).** A project layer has no build step and only `import type`, so it cannot ship React, routes or Service methods. Its UI and capabilities instead go through three generic parts:
- **Handlers.** `createHandlers(ctx): LayerHandlers`, the type exported by `agent/layer-context.ts` = `{ queries?: Record<string, (input: Json, ctx: Context) => Promise<Json> | Json>; actions?: Record<string, { replay: "safe" | "unsafe"; run(input: Json, origin: Origin, ctx: Context): Promise<Json> }> }`. Handler names match `^[a-z][a-z0-9_]{0,63}$`. State lives where the layer chooses (a JSON file under `tsf/data/layers/<name>/`, or the layer's own table in `tsf.sqlite` through `ctx`); the layer publishes `layer.changed` through `ctx.bus` when it changes state itself.
- **Service and routes.** `layerQuery({ layer, name, input })` and `layerAction({ layer, name, input }, origin)` validate that the layer is loaded and enabled and the handler exists (`not_found` otherwise), run an action under the mutex key `layer:<name>`, then publish `layer.changed { layer, by }`. Routes: GET `/api/layers/:layer/query/:name?input=<url-encoded JSON>`, POST `/api/layers/:layer/action/:name` with body `{ input }`. A layer tool that mirrors an action calls `ctx.service().layerAction(...)`, so routes, tools and UI share one Service method (principle 2).
- **UI.** Manifest contributions are data (`LayerControl` in `shared/types.ts`): a widget is one control, a settings panel is a list of controls, a hotkey runs an action or opens a panel. `web/layers/LayerControl.tsx` renders each kind with pw-ui (`value` text, `button` + optional `ConfirmDialog`, `toggle` Switch, `text`/`number` Input with save, `select` Select), fetching queries on mount and on `layer.changed` for its layer. It is the only file allowed a dynamic `data-cap={control.capability}`; parity check 4 reads layer control ids from the manifests instead of scanning for literals (section 10). Settings panels appear in their `section` of the Settings modal; widgets appear in `list_widgets` and can be placed by id `<layer>.<widget>`.
- **Capabilities.** `LayerManifest.capabilities` entries name `kind` + `handler`, a `tool` and a `control` (both required); the Service method and route are derived (section 10).

**Declarative layers, core bindings, authoring and reload (P9).**
- **`manifest.json` (D1).** A project layer folder may hold `manifest.json` instead of `manifest.ts` (both present: the layer fails with "both manifest.ts and manifest.json exist"). It is a `LayerManifest` as JSON, `kind` `"harness"` only, validated strictly by `agent/layer-manifest.ts` `parseJsonManifest`: unknown keys are rejected at the top level and in every object, every problem is reported with its path (`ui/widgets/0/control/label: ...`), `enabledByDefault` defaults to true and `env`, `vaultHosts`, `ui`, `capabilities` to empty. `extension.ts` is optional for such a layer: without it the registry synthesises `defineExtension({ name, sections })` with no tools and one prompt section per `prompts/<file>.md` (key `<layer>-<file>`, file name `^[a-z][a-z0-9_-]{0,40}$`, title = the first `# ` heading else the file name, shown by `list_prompts`; text read at load, empty file renders nothing; on/off like any section). With `extension.ts` the usual `createExtension` / `createHandlers` apply (`handlers` are the `createHandlers` export; there is no separate `handlers.ts`). A json layer's capabilities must name a tool of its extension, a handler of `createHandlers` and a control that carries the id.
- **Core bindings (D2).** A `LayerControl` `query`, `action` or `optionsQuery.query` may be `core:<capabilityId>`: a query binding names a non-mutating capability with a GET route, an action binding a capability with a POST route (checked at validation; code layers (`manifest.ts`) get the same check on their `core:` names only). `capability` is a LayerCapability id of the layer or a core capability id (json layers). `field` may be dotted (`model.modelId`; through null or a missing key it reads null). `select` takes `options` (fixed) or `optionsQuery { query, field?, valueField?, labelField? }` (exactly one). Toggle, text, number and select controls may carry `actionInput`, a JSON object template where every string `"$value"` is replaced by the `{ value }` the web sends. Resolution is in `Service.layerQuery` / `layerAction` (`core/core-bindings.ts`): the layer must be loaded and enabled and its manifest must declare that exact `core:` name (a layer's routes cannot proxy other capabilities); the capability's own Service method runs (`capability.service`), a core action takes the capability's keys instead of `layer:<name>` (lock order) and then publishes `layer.changed` for the layer. Input shaping: `getRun` takes `input.id`, `setThinkingLevel` `input.level`, `unselectPage`, `refreshModels` and `clearRuntimePrompts` take only the origin; `core:model.set` accepts `{ modelId }` alone and finds the provider in the catalog (`invalid` when the id exists under several). The model picker is `template/examples/model-picker.layer.json` (tested end to end in `tests/unit/layers-authoring.test.ts`): query `core:settings.get` field `model.modelId` (null until a model is stored), `optionsQuery { query: "core:models.list", valueField: "id", labelField: "name" }`, action `core:model.set`, `actionInput { "modelId": "$value" }`, capability `model.set`.
- **Reload (D3).** `registry.reload()` rescans `tsf/layers/*/`, rebuilds changed layers (signature = mtime and size of `manifest.json`, `manifest.ts`, `extension.ts` and `prompts/*.md`; the signature now covers every file below the layer folder, so editing a helper module alone reloads the layer). **Fresh imports under tsx:** the real launcher registers the tsx loader, which refuses a cache-busting query on a `.ts` URL (`Cannot find module '.../extension.ts?t=<mtime>_<size>'`, event `layer.failed`; vitest's own loader accepted it, which hid the bug). A project layer's code is therefore imported from a copy of its whole folder at `tsf/data/layer-cache/<layer>/<hash of the file stamps>/` (`freshCopy` in `agent/registry.ts`): every import inside the layer gets a new URL, relative imports keep working, an edit gives a new hash, the two newest copies per layer are kept and the cache is emptied at startup. Built-ins are imported in place. `tests/integration/layers-launcher.test.ts` runs the real launcher against an `extension.ts` with a helper, `createHandlers` and a `manifest.ts` layer, validates, rebuilds the tool map and the ceiling (same permissions file content as read at startup, applied to the new tool map; the guard reads `ctx.ceiling()` through the registry, so it follows) and swaps the registry state in place (`ReloadResult { added, removed, changed, failed }`). A project tool name that clashes with a built-in or an earlier layer fails the later layer (startup keeps D8: it still throws). Built-ins and provider layers are never reloaded (a new provider layer needs a restart and is marked failed). `agent.reloadLayers()` then installs added and changed extensions in pi-durable's registry (keyed by name), uninstalls removed ones, drops the settings cache and re-applies `configure({ extensions: { add, remove } })` against the current selection. The Service publishes `layers.changed` (LayerInfo carries `ui`, `status`, `error`, `sections`), `tools.changed`, and, when layers were added, removed or changed, `settings.changed` (`layersEnabled`) and `prompts.changed`; after releasing the `layers` mutex it binds the default keys of new layer hotkeys and removes placements whose widget type no longer exists or no longer fits its navbar (`ui_config.changed`), so a stale placement never makes `update_ui_config` fail its check.
- **Authoring (D4, section 5.1 and 10).** `createLayer`, `deleteLayer`, `writeLayerFile`, `deleteLayerFile`, `reloadLayers`, `defineWidget`, `removeWidgetType` take the `layers` mutex and end with a reload; `listLayerFiles` and `readLayerFile` also work for built-in layers (read-only). Only project layers are writable, never through a symlinked folder. A path is POSIX and relative to the layer folder: absolute paths, `..`, `.` and dot segments, backslashes and any symlink on the path are refused, only `.json`, `.ts` and `.md`, at most 256 KiB, at most five segments deep. `manifest.json` is validated before it is written (invalid: `invalid`, file untouched); other files are written and the answer carries the reloaded `LayerInfo` (`status: "failed"` with `error` when the layer no longer loads). `manifest.json` and `manifest.ts` cannot be deleted by `deleteLayerFile`. `defineWidget` / `removeWidgetType` edit the `ui.widgets` of a `manifest.json` layer (a `manifest.ts` layer: `invalid`, "edit that file with write_layer_file"), validate the whole manifest, and restore the old file when the reloaded layer fails. `deleteLayer` refuses built-ins (`forbidden`), removes the folder, drops `layerToggles[name]` and the placements. The coding tools keep their denial under `tsf/layers`: these tools are the sanctioned path, and `ceiling.ts` is unchanged.
- **Versions, requires and default placements.** `LayerManifest` gains `version` (semver; required in `manifest.json`, optional in `manifest.ts`; `createLayer` writes `"0.1.0"`), `origin` (free text, a URL or `"local"`; `createLayer` writes `"local"`, an https import records its URL) and `requires { core?: <semver range on the app's package.json version>, layers?: string[] }`. `shared/semver.ts` is a small dependency-free subset (`^ ~ >= > <= < =`, `x` ranges, `||`). After the project layers are built, `registry.build` fails (status `"failed"`, `error: "layer <n>: requires core >=1.0.0, but this factory is 0.9.0"` or `"requires layer <x>, not loaded"`) every layer whose requirement is unmet, repeating until stable so a layer that needed a failed one fails too; never fatal. `LayerInfo` carries `version`, `origin` and `requires` (also for a failed layer whose manifest parsed) and the layer row in Settings > Advanced shows them. `WidgetContribution.defaultPlacements?: { navbar, slot }[]` (navbar must be one of the widget's `navbars`): `Service.applyDefaultPlacements` runs at boot and after every layer change (inside `syncUiWithLayers`): for each loaded layer's widget type that has defaults and is not yet recorded, it places the widget at each default when no placement of that type exists anywhere, then records the widget id in the layer's own state file `tsf/data/layer-state/<layer>.json` (`{ "appliedPlacements": [...] }`). The record also covers a type that was already placed, so removing the widget later, or disabling and re-enabling the layer, never brings it back; `deleteLayer` removes the state file. Redefining a widget does not re-place it.
- **Export and import (capabilities `layers.export`, `layers.import`, phase 9).** `exportLayer({ name, to? })` archives a project layer (`.json`, `.ts`, `.md` files below the folder, dot entries, `node_modules` and symlinks skipped) as a gzip-compressed ustar tar (`core/layer-archive.ts`, node's zlib, no dependency; mode 0644 and mtime 0 so equal files give equal bytes) into `tsf/data/exports/<name>-<version>.tgz` (or `to`, a plain file name ending `.tgz` or `.tar.gz`) and answers `{ name, version, path, file, size, files }`; a built-in is `forbidden`. `importLayer({ source, name?, replace? })` reads a local `.tgz`, a local layer folder (relative paths resolve against the project root) or an https URL to a `.tgz`, then: every entry path must pass the same `checkRelPath` as `write_layer_file` (so `../x`, absolute paths, dot segments and other extensions are refused with the entry named), only regular files and folders are accepted (links and devices are refused), at most 500 files, 256 KiB each, 4 MiB unpacked and 4 MiB compressed; one top-level folder holding the manifest is stripped; a `manifest.json` is validated with `parseJsonManifest` (the loader's own validator); the layer name is `name` or the manifest's (a `manifest.ts` layer needs `name`); a declarative layer without `.ts` files can be installed under another name, and every `<old>.<x>` id (widget, panel, capability, hotkey and references) is renamed; an existing layer is refused (`conflict`) unless `replace: true`. The files are written to a dot folder and renamed into `tsf/layers/<name>` under the `layers` mutex (a failed import leaves nothing), then the registry reloads: an unmet `requires` therefore shows as a `failed` layer in the answer, not as an error. The download uses the global `fetch`, so the environment's proxy settings apply (Agent Vault code rules: no custom agent, no credentials sent, nothing printed about the proxy; a transport failure is reported as `could not download <host> (<code>)` only). Imports are user-initiated, so the inbound `TSF_ALLOWED_HOSTS` list does not apply; only https is accepted, redirects must stay on https. Imported code runs in the server like any project layer (section 14, item 12), so import only layers you trust. UI: Settings > Advanced > Layers has Import layer next to New layer and an Export button per project layer that reports the archive and links its download.
- **Select options: sort and group.** `SelectOptionsQuery` gains `sortBy` (`"value"` or `"label"`), `numeric` (digits compare as numbers, `Intl.Collator`) and `groupBy` (`{ field }`, a string field of each object item, or `{ prefix }`, the separator: the part of the value before its first occurrence, `"/"` puts `openrouter/anthropic/claude` under `openrouter`). Validated in `layer-manifest.ts`; shaped by `shared/select-options.ts` `shapeOptions` (shared by the web renderer and the tests): options without a group come first, groups follow sorted by the same collator, and `LayerControl` renders each group as an `<optgroup>`. The model picker example sorts by label, numeric, grouped by the id prefix before `/`, and has `defaultPlacements` in the agent navbar, right slot.

**Ceiling (`agent/ceiling.ts`, D7, D8).**
- File: `{ "allow": string[], "deny": string[] }`; missing file = `{ allow: ["*"], deny: [] }` with `source: "default"`. A missing `allow`, malformed JSON or a pattern that is not a non-empty string throws (fail closed); a missing `deny` means none. `readCeiling` returns `CeilingRead { file, source, cli, path, sha256 }` (`sha256` null when the file is missing); `Ceiling` exposes `sha256` and `info()`; `outsideCeiling(ceiling, tool)` and `blockedResult(ceiling, tool)` are exported helpers.
- Pattern: `<layerGlob>.<toolGlob>`; `*` alone means `*.*`; a pattern without a dot means `<layer>.*`. `*` matches any run of characters, `?` one character, everything else literal; case-sensitive; compiled to an anchored RegExp per segment.
- Verdict for tool `t` of layer `l`: `allow` matches `l.t` and no `deny` matches `l.t` (deny wins). With `--tools p1,p2`: additionally some `--tools` pattern matches (an AND, so it can only narrow); an empty `--tools` list (given, not absent) allows nothing.
- The verdicts are computed once over the tool map into a frozen `Set<string>` of allowed tool names. No code path re-reads or writes `permissions.json`; there is no setter.
- Guard: factory_harness installs one `hook(ToolTask, { beforeTool, afterTool })`, reading `ctx.ceiling()` at call time. `beforeTool`: `ceiling.allowsName(call.name) ? undefined : { block: \`outside the permissions ceiling: ${layer}.${call.name}\` }` for any resolved call, nested ones (`call.parent`) included. A call to a tool that is not registered never reaches `beforeTool` (the tool task settles `tool_unavailable` first; read in `harness/tool.js`), so `afterTool` covers it: when the result's first diagnostic is `tool_unavailable` and the registry's tool map knows the name as denied, it returns `{ isError: true, output: [], diagnostics: [{ severity: "error", code: "blocked", message: "Tool call blocked: outside the permissions ceiling: <layer>.<tool>" }] }`. The output is empty because pi-durable already writes each diagnostic into the model's tool-result content as `<harness>\n[error] <message>\n</harness>`; a text output would repeat it, and the empty form matches the Harness's own `blocked` result. The tool item's output still carries the message. Unknown names and tools the user disabled keep `tool_unavailable`. Probed on 1.5.0: a faux call to an unregistered `bash` runs only `afterTool` (with `{ output: [], isError: true, diagnostics: [{ code: "tool_unavailable" }] }`), settles with diagnostic `blocked` and that text, and `beforeTool` is not called for it; a registered tool blocked by `beforeTool` reaches `afterTool` as `blocked`. **Acceptance 10 ("an injected direct call is blocked"):** the faux model calls a denied tool (`probe bash`); filtering keeps it out of `/api/tools` and the request's tools, and the guard answers with the `blocked` result naming the ceiling (tool item status `blocked`), so filtering and hook are both tested. The test seam `testing.skipCeilingFilter` additionally proves `beforeTool` for a tool registered past the filter, and `set_tool_enabled` / `POST /api/tools/set-enabled` for a denied tool returns `forbidden` (P5).
- factory_harness is `required`: Service refuses to disable it and the extension edit never removes it, so the hook is always selected.
- `setToolEnabled(name, true)` for a name outside the ceiling is `forbidden` with "outside the permissions ceiling".

**RootedEnv (D4).** `class RootedEnv extends NodeExecutionEnv` (constructor `{ cwd: string; shellPath?; shellEnv?; watch? }`) overrides `absolutePath(path, context): Promise<Result<string, FileError>>`:
1. `abs = await super.absolutePath(path, ctx)` (lexical resolve against cwd; return its error unchanged).
2. Canonicalise for symlinks without requiring the path to exist: `NodeExecutionEnv.canonicalPath` is `realpath` and returns `not_found` for a missing path, which would make `write` fail for every new file and give `read`/`edit` of a missing file the wrong error. So walk up from `abs` to the deepest existing ancestor (`fs.lstat`, stop at the first that exists), `realpath` that ancestor, and re-append the missing remainder (which cannot contain symlinks because it does not exist). The project root is `realpath`ed once in the constructor.
3. Return `err(new FileError("permission_denied", "outside the project: <path>", path))` (`err` and `FileError(code, message, path?, cause?)` from `@earendil-works/pi-durable/env`) when the canonical path is not inside the canonical root, or `"protected path: <rel> is not available to file tools"` when it is inside a protected path (`PROTECTED`): `tsf/permissions.json`, `tsf/.env`, `tsf/data/`, `tsf/layers/` and `tsf/mod.just`; the harness adds the skill folder when the project contains it (`protectedPaths(root, skillDir)`; a project that is the skill folder gets `.`, everything). `tsf/layers/` and `tsf/mod.just` are code the factory runs without asking (project layers are imported into the server at the next start, unsandboxed; the mod launches it), so writing them would widen the ceiling; reading them is denied too, because `absolutePath` does not know the operation (the agent lists layers through `factory_controls`). Protected paths are canonicalised on every call (a symlinked `tsf` or `tsf/data` is still caught) and compared case-insensitively on macOS and Windows. A dangling symlink is followed by hand with `readlink` (40 hops at most), since a write through it would create the file at its target; a path that cannot be resolved (ELOOP) is denied. `RootedEnv.root` is the canonical root.
4. Otherwise return `ok(abs)`: the tool's own error for a missing file (`not_found` from `read`) is then the library's. 
`read`, `write` and `edit` resolve every path through `env.absolutePath` (pi-durable `tools/path-utils.js` `resolveToolPath`), so this one override is sufficient. One theoretical gap: `read`'s `resolveReadToolPath` then probes Unicode-normalised variants (NFC/NFD, space characters) of the checked path through `env.exists`, which is not re-checked; the variants differ only in normalisation (section 14). Compile-probed: `class RootedEnv extends NodeExecutionEnv` with this signature type-checks on 1.5.0. `bash` runs with `cwd` = project and is **not confined by path**: enabling `coding_tools.bash` is a ceiling decision equal to full trust.

### Liquid core (P9)

The principle: the agent can change anything in its own factory, including the factory app's web and server source. The unit of sharing stays the layer (export and import, section 8); the core copy in `tsf/app` records its base (`.tsf-base`), so a core edit is a diff against a known skill version. The pieces, each a capability with a tool and a control (section 10):

- **Source in the project.** `tsf/app` (section 2). File tools reach everything in it except `node_modules` and `.tsf-base`; `package.json` is editable, and the launcher installs on the next start because the install hash changes. Built-in layers in `tsf/app/src/layers` are code like any other there; the layer tools still treat them as built-in (read-only).
- **Web (`factory.rebuild_web`).** Edits to `src/web` and `src/shared` rebuild live and swap in with a page reload; a failed build keeps the last good one and says why (section 3 "Live web rebuild"). `rebuild_web` runs the build now and returns `{ ok, hash, error?, durationMs }`; Settings > Advanced > Factory has a "Rebuild web" button (`data-cap="factory.rebuild_web"`) that shows the result.
- **Server and core (`factory.restart`).** Edits there take effect at a restart (section 3 "Restart"); `restart_factory` (replay `safe`: a replayed call id restarts nothing) and the "Restart factory" button (a pw-ui `ConfirmDialog`, `data-cap="factory.restart"`).
- **Seeing the UI (`ui.screenshot`).** `core/screenshot.ts` imports `playwright` (a runtime dependency pinned to the same version as `@playwright/test`) lazily, launches headless Chromium, opens the factory's own listening URL on loopback (`0.0.0.0` becomes `127.0.0.1`; the `page` argument must be an app path starting with a single `/`), waits for `load`, for network idle (best effort: the event stream never idles) and for the connection badge to be live, sets the colour mode when given (`colorScheme` emulation and `<html data-theme>`), and writes `tsf/data/screenshots/<ISO timestamp>.png`. The result is `{ path, file, url: "/api/screenshots/<file>", width, height }` (width and height read from the PNG). Browsers are installed separately and never by the factory: a missing browser answers `unavailable` naming `npx playwright install chromium` run inside `tsf/app`, and a failed `import("playwright")` answers `unavailable` as well, which is how the tool reports itself unavailable. The tool returns the JSON as text and the PNG as an image content block (pi-durable's tool result `output` carries `image` blocks, as its own `read` does; `defineAppTool` has an `attach` hook for it), because `tsf/data` is protected from `read`; the control shows the image inline from `/api/screenshots/<file>`.
- **Guidance.** `RULES_TEXT` of `factory_controls` tells the agent where the source is, what rebuilds live, what needs a restart, to prefer a layer and to add an extension point to the core when a feature needs one, to use `screenshot`, and what `.tsf-base` is.
- **Status and events.** `FactoryStatus.web = { hash: string | null, building: boolean, lastError: string | null }`; bus events `web.rebuilt { hash }`, `web.build_failed { error }`, `factory.restarting { inMs, reason?, by }`.
- **Parity.** The three capabilities' routes answer without side effects under `{}`: all three answer `conflict` in the in-process test factory (no restart hook, no served web), which parity accepts (not 404, 405 or 5xx).

## 11. Web app

## 12. Environment and keys

- Keys come only from the environment. `core/env.ts` loads `tsf/.env` with `parseEnv` (comments, `export`, quotes) and sets a variable only when it is unset or empty, so `/etc/agent-vault.env` from systemd's `EnvironmentFile` always wins.
- Vault rules: routing only from `HTTPS_PROXY` + `NODE_USE_ENV_PROXY=1`; global `fetch` only, no `ProxyAgent`, `setGlobalDispatcher`, `fetch:` or `env:` option passed to pi-ai; keys read as `OPENROUTER_API_KEY` and `TYPESAFE_API_KEY` with a blank-only guard (the placeholder `agent-vault` passes); never validate key format; keys only in `Authorization: Bearer`; hosts limited to `openrouter.ai` and `api.typesafe.ai`; never write `NO_PROXY`, never disable TLS checks; never log or show `HTTPS_PROXY` or key values (status and Settings show presence by name). Checked by grep over `src` at P8: no `ProxyAgent`, `setGlobalDispatcher`, `NO_PROXY` or TLS-disabling option exists, and `HTTPS_PROXY` appears only in comments (the app never reads or logs it). The P7 lot recorded a live jev call through the vault wrapper (section 14).
- `.env.example` (stamped): blank `OPENROUTER_API_KEY=`, `TYPESAFE_API_KEY=`, `TSF_HOST=127.0.0.1`, `TSF_PORT=8000`, a comment that `agent-vault` is the value on a vault-routed VM, and commented `# TSF_MODEL_PROVIDER=faux`.
- `TSF_HOST`/`TSF_PORT` validated (integer 0..65535; 0 picks a free port for tests). Other variables: `TSF_ALLOWED_HOSTS` (comma-separated host names the API accepts besides `localhost`, `*.localhost`, IP literals and the listen host; section 5 request guard), `TSF_PROJECT`, `TSF_SKILL_DIR` (read by `tsf/mod.just` only), `TSF_MODEL_PROVIDER` (`faux` runs the scripted model), `TSF_JEV_PROVIDER` (`faux` answers jev locally), `TSF_FAUX_RULES`, `TSF_FAUX_TPS`, `TSF_VITE_URL`, `TSF_LOG_LEVEL`, `TSF_SYSTEMD_DIR` (tests). On the laptop, `av just tsf start` runs the factory under the `av` wrapper (it opens the tunnel to the vault proxy, exports the placeholder `agent-vault` keys and routes through the proxy).
- **exe.dev bind address (spec 9): `TSF_HOST=0.0.0.0` on a VM.** The app is served at `https://<vm>.exe.xyz`; the proxy terminates TLS outside the VM, so it reaches the server through the VM's network interface, not its loopback, and a loopback-only bind would be unreachable (an inference: no VM was available to the design). The exe.dev proxy docs (checked 2026-11-03) say it forwards ports 3000-9999, the public one picked from the VM's `EXPOSE` (prefer 80, else the lowest ≥ 1024) or set with `ssh exe.dev share port <vm> <port>`, and do not name a bind address; so the VM's `tsf/.env` sets `TSF_HOST=0.0.0.0`, `TSF_PORT=8000` and `TSF_ALLOWED_HOSTS=<vm>.exe.xyz` (the request guard refuses any other Host name; if the proxy rewrites Host to an IP, the Origin check still accepts `https://<vm>.exe.xyz` through the same variable; the deployment check will show which), the laptop keeps `127.0.0.1`, and a deployment check on a real VM is to confirm it (if `127.0.0.1` also works there, keep `0.0.0.0` anyway: it is what the proxy needs in general). **exe.dev check (2026-11-03, VM `tsf-check`).** On a real sandbox the proxy passed the public host name through (checked in a signed-in browser; from outside, a non-public VM answers 307 to `/__exe.dev/login`), `ping` was answered through the vault with the placeholder key, the VM has no zsh (so the mod's shell is bash), and pw-ui's `dist/react` needs `radix-ui` and `lucide-react` from the app's `node_modules` (declared by the app and deduped in `vite.config.ts`). There is no in-app auth, so whatever reaches the port controls the factory; only users with VM access reach non-public ports.
- systemd: a **system** unit (exe.dev VMs run systemd as PID 1; a user unit would stop at logout without lingering), `tsf-<project-dir-name>.service`, written by `scripts/vm-tsf.sh` (run by `push.sh` and `base-image.sh`; the app CLI no longer installs units). It has `User=<VM user>`, `WorkingDirectory=<project>`, `TSF_PROJECT`, `TSF_SKILL_DIR=~/.local/share/tsf/skill`, `PATH=/usr/local/bin:/usr/bin:/bin` (the launcher may run `npm install` and `vite`), `TSF_SUPERVISED=1` (the agent's restart exits 3), `TSF_HOST=0.0.0.0`, `TSF_PORT=8000` and `TSF_ALLOWED_HOSTS=%H.exe.xyz` (the VM's hostname is its name; these win over `tsf/.env`, so a `.env` pushed from the laptop cannot move the port), `EnvironmentFile=-/etc/agent-vault.env`, `ExecStart=<node> <project>/tsf/app/bin/tsf.mjs start` (the skill's launcher for a `--no-app` project), `Restart=on-failure`, `RestartSec=3`, `KillSignal=SIGTERM`, `TimeoutStopSec=15`, `WantedBy=multi-user.target`; no keys. A path unit, `vault-env-restarts-tsf.path`, runs `systemctl try-restart tsf-*.service` when `/etc/agent-vault.env` changes, because pw-sandbox's first boot writes that file after a fresh copy of the base has already started its TSF. Interaction with `stop`: the server exits 0 on SIGTERM, which `Restart=on-failure` does not restart, but systemd would still show the unit as stopped while enabled; so when `/etc/systemd/system/<unit>` exists, `stop` prints "managed by systemd: sudo systemctl stop <unit>" and does nothing unless `--force` (section 3). `status` adds a `systemd <unit> (installed)` line when the process runs, and a `sudo systemctl start <unit>` hint after `not running` when the unit file exists (exit codes unchanged). `start` while the unit runs fails on the PID lock with the owning pid.
- **Launching on a VM.** `scripts/push.sh` is layered on `pw-sandbox push`, which creates a persistent VM by copying the base image `tsf-base-img` (tailnet, Agent Vault) and copies the folder, `.env` and `tsf/data` included, to `~/<folder>`. push.sh pushes the git toplevel and then: syncs the skill to `~/.local/share/tsf/skill`; copies `~/.gitconfig` without machine-specific keys; on the VM removes the laptop's `server.json`, PID lock and `tsf/app/node_modules` (built for another platform; the launcher's install hash ignores the platform), stamps a TSF when the repo has none (the laptop repo is never stamped), writes `tsf/.env` with placeholder keys when there is none, removes a `faux` provider line, retires every other TSF unit (the base image's empty TSF at `~/empty-factory` is stopped, its folder kept) and installs the unit. pw-sandbox push only creates VMs, so naming an existing VM (tagged `sandbox`, running, Node 24) makes push.sh copy the folder itself with pw-sandbox's tar command. That is refused when the VM has a TSF unit other than the baseline or already has `~/<folder>`, unless `--force`; `--force` prints what it will wipe (each TSF unit and its `tsf/`, data included, and `~/<folder>`) and reads y/N on stdin before any change. `push.sh --empty` runs `pw-sandbox new --keep` from the base. `scripts/base-image.sh` keeps the base up to date and pauses it with the TSF stopped, so no live pid is copied. `install.sh` options: `--no-app` and the environment variable `TSF_INSTALL_NO_APP=1`; the test helpers (`tests/helpers/project.ts`, the e2e global setup) set it so tests run from the skill app with no per-project `npm install`.
- **VM skill path.** A pushed project keeps the laptop's stamped skill path in `tsf/mod.just` (install never overwrites). It matters only for a `--no-app` project, and the unit and `~/.bashrc` set `TSF_SKILL_DIR` to the VM's copy; nothing is re-stamped.

### Known gaps (accepted, visible)

1. **Crash window.** `progress.persistWithinMs` is 1 000 ms: a kill loses up to about one second of streamed text or tool output, and an attempt that crashes in its first second may leave no aborted entry and no usage record.
2. **Memo-then-effect ordering.** `once()` runs the effect, then stores the memo; a crash between them repeats the effect. Only effects keyed by `callId` (sqlite rows, pi-durable request ids) are idempotent; a page write is not, so page tools are `unsafe` (at most once).
3. **Two stores.** `agent.sqlite` and `tsf.sqlite` cannot commit atomically; settings applied with `configure` are re-applied in full at boot to converge.
4. **bash** is unconfined by path and can edit `permissions.json` (effective at the next start; detected and shown, see "Spec mismatches"), write a project layer under `tsf/layers/` (imported unconfined at the next start; not detected) or kill the server (systemd restarts it). Deny `coding_tools.bash` where the agent is not fully trusted; `write` and `edit` cannot reach `tsf/layers/`, `tsf/mod.just` or the ceiling (T12).
5. **PID reuse.** A stale lock whose pid was reused by a live process blocks startup; remove `tsf/data/agent.sqlite.lock` by hand.
6. **No in-app auth.** Binding beyond loopback exposes full control. The request guard (section 5) stops other web pages (cross-site requests, DNS rebinding), not anyone who can reach the port.
7. **Ring memory.** 500 deltas with whole `ChatLive` payloads can reach several MB during a long streamed answer; acceptable for one factory.
8. **Freshly published pins.** Several latest versions are under two weeks old.
9. **Vendored pw-ui.** The app stays on the committed pw-ui version until someone runs `just upgrade-pw-ui`, and a project's own `tsf/app` keeps its version until it is reset.
10. **First start is slow.** `npm install` plus a blocking Vite build (tens of seconds) before the URL line on a fresh skill checkout or after a web source change.
11. **RootedEnv Unicode variants.** `read` probes Unicode-normalised variants of an already-checked path through `env.exists` without re-checking them (section 8). The variants differ only in normalisation and space characters, so they cannot leave the project in practice.
12. **Project layer code runs unconfined, and the agent can now write it (P9).** A project layer's `extension.ts`, `manifest.ts` and `createHandlers` run in the server process with the server's rights, as before: nothing confines them (`bash` could already plant a layer, and the ceiling does not cover layer code). The agent now reaches that code through `write_layer_file` (the coding tools' `tsf/layers` denial is unchanged, so this is the one sanctioned path), which is the same trust level as `bash` plus a restart, but a layer is now loaded at once and the change is validated (names, manifest shape, tool clashes, `core:` bindings), recorded in the log (`layer.file_written` with the origin) and shown in `list_layers` as `loaded` or `failed`. Declarative layers (`manifest.json` with prompts and widgets, no `extension.ts`) carry no code; their `core:` bindings reach only capabilities the UI and the agent already have. Ceiling patterns still apply to a layer's tools, read from the file as it was at startup (`permissions.json` is not re-read by reload). A `.ts` module's old versions stay in Node's module cache (one entry per edit) until restart.
13. **Layer sharing is primitives only (P9).** Export and import move one layer as a `.tgz`; there is no registry, signature or trust model, so an imported layer's code is trusted by whoever imports it (see item 12). Layers have no dependency resolution beyond `requires` (a core range and loaded layer names). Not verified on a VM: the https download through the Agent Vault proxy (unit-tested with a stubbed `fetch`); `package.json` now carries `version` (0.9.0), so the launcher's install hash changes once and runs `npm install` on the next start.
14. **No upgrade merge of `tsf/app` (P9, deferred).** Re-stamping keeps an existing `tsf/app`; there is no way to bring a newer skill's core into an edited copy except a fresh stamp (which discards the edits) or by hand. `.tsf-base` holds the base version and commit, so a three-way merge (base, the copy, the new skill) is possible; it is not built. The same record would let the app export the agent's core changes as a diff against the base (`diff -ru` of the skill at `commit` against `tsf/app`); that export is not built either, so a core edit is shared today only as the layer that ships the feature.
15. **The agent can break its own server (P9).** A server or core edit that does not compile or throw at start leaves the process unable to boot after `restart_factory`; under systemd `Restart=on-failure` loops every 3 s and the web is down with it. Nothing rolls the copy back. The recovery is by hand (edit the file, or copy the skill's app back), and `tsf/app/.tsf-base` names the version to restore. Web edits cannot do this: a failed build keeps the last good one.
16. **Skill-run server with a project copy (P9).** Starting the server from the skill's launcher in a project that has `tsf/app` runs the skill's app entirely (never the copy) and logs `startup.app_mismatch`; the copy's edits are not in effect until the copy's launcher runs. `just tsf start` and the VM unit pick the copy. A `manifest.json` without `version` loads as 0.1.0 so layers written before versions keep working.

### Review answers where the design keeps its position

- **just functions.** `parent_directory(source_directory())` in a mod file was checked on just 1.46.0: it gives the folder holding `tsf/`, and `set working-directory := ".."` gives the same folder as `$PWD`.
- **Type name clashes (round 2).** TSF keeps `ThinkingLevel`, `Page`, `Settings`, `RunSummary`; renaming them would touch every contract consumer for a minor risk. The rule in section 7 (library types under a namespace import) prevents a silent wrong import.
- **Ceiling widening by bash (round 2).** Detection stays the mitigation (hash logged and shown, warning banner); preventing it needs a confined shell, which pi-durable does not offer. The spec owner decides (section 14, spec 2.5 row).
- **Acceptance 10 hook (round 2).** The decision said the `beforeTool` guard answers a call to a denied tool. pi-durable 1.5.0 settles an unregistered call `tool_unavailable` before `beforeTool` runs (`harness/tool.js`), so the same guard registration answers it from `afterTool` (T27); the outcome the decision asked for, `blocked` naming the ceiling, is unchanged.
